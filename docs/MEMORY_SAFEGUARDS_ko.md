# OMR API 메모리 보호 (2026-11-04)

## 확인한 원인과 범위

기존 코드(85215b0)는 스캔을 전체 컬러로 읽은 뒤 그레이스케일 복사본을 만들고,
원본 크기 전체에서 QR을 검출했다. OpenCV의 기본 병렬 처리도 임시 버퍼를 늘린다.
`/read`만 동시 처리 수를 제한하여 `/generate`, `/preview`는 판독과 동시에 실행될 수 있었다.
PDF는 페이지 크기를 확인하지 않고 모든 페이지를 먼저 PNG로 펼쳤다.

합성 A4 600dpi 스캔 1장(7017 × 4962, QR 학번 포함), 미리보기와 서술형 크롭을
함께 켠 API 작업 함수를 새 프로세스에서 반복 실행한 측정:

| 코드 | 반복 | 최대 RSS |
| --- | ---: | ---: |
| 변경 전, OpenCV 기본 9스레드 | 3 | 598.1 MiB |
| 변경 후, OpenCV 1스레드 | 20 | 331.4 MiB |

약 45% 감소했고 변경 후 20회 모두 정상 결과를 반환했다. Python 3.12 / OpenCV 5.0.0 /
Linux 환경에서 측정한 프로세스 RSS이며 Render 컨테이너의 전체 메모리 측정이 아니다.
운영 Docker는 Python 3.11이고 의존성 버전이 고정되어 있지 않으므로 운영 수치와 다를 수 있다.
원래 장애를 일으킨 업로드 파일과 요청별 메모리 기록은 확보하지 못했다.
따라서 512MiB를 초과하는 코드 경로를 재현한 것이며, 특정 운영 장애의 입력을 확정한 것은 아니다.

## 변경 사항

- 기존 컬러→그레이스케일 변환을 그대로 사용해 채점 픽셀을 보존하고, 변환 직후 컬러
  복사본을 해제한다. QR·마커 검출 중에는 컬러 원본을 붙잡아 두지 않는다.
- QR 검출용 이미지만 긴 변 2500픽셀로 제한한다. 작은 이미지에서 QR 위치를 찾았지만
  내용을 못 읽으면 원본의 QR 영역만 잘라 다시 읽는다. 축소 이미지에서 위치도 찾지 못하면
  모서리부터 겹치는 원본 해상도 타일을 차례로 확인한다(각 타일도 긴 변 2500픽셀 이하).
  채점용 마커 검출·원근 보정·서술형
  크롭은 원본 해상도를 사용하고, 채점 기준·레이아웃 지문·문항 규칙은 변경하지 않는다.
- 이미지 헤더를 먼저 확인한다. 40,000,000픽셀 또는 한 변 10,000픽셀을 넘으면
  디코딩 전에 명시적인 오류를 반환한다. A4 600dpi는 허용한다.
- `/read`, `/generate`, `/preview`가 같은 처리 슬롯을 사용한다. 취소된 요청도 실제 작업
  스레드가 끝나기 전에는 슬롯과 임시 파일을 해제하지 않는다. `/health`는 별도로 응답한다.
- API OpenCV 스레드 기본값은 1이다. `OMR_OPENCV_THREADS`로 바꿀 수 있지만 작은
  인스턴스에서는 1을 유지한다. `/health`의 `opencv_threads`에서 설정을 확인한다.
- PDF는 200dpi를 유지하고 한 페이지씩 렌더링·판독·삭제한다. 픽스맵과 MuPDF 캐시를
  판독 전에 해제한다. 렌더링 전 모든 페이지의 크기를 확인하여 12,000,000픽셀 초과
  페이지는 오류로 돌려준다. 100페이지 초과 PDF를 조용히 잘라내던 동작 대신 파일을
  나누라는 명확한 오류를 반환한다.
- `/generate`에서 PNG 미리보기를 요청할 때는 50~300dpi만 허용한다. `/preview`의
  기존 50~150dpi 범위는 유지한다.

## 재검증

```bash
python -m pytest tests/ -q
python -m compileall -q omr omr_api tests scripts
python scripts/profile_read_memory.py scan.png template.json --iterations 20
```

비교할 때는 같은 입력을 쓰고 새 프로세스에서 실행한다. 벤치마크의 `--repo` 옵션으로
별도 체크아웃을 지정할 수 있다. 합성 입력 생성은 측정과 별도 프로세스에서 해야 생성기의
최대 메모리가 섞이지 않는다. 벤치마크 출력에는 학생 정보나 판독 답안을 넣지 않는다.

## 운영 적용 전 확인

이 변경 자체는 서비스 설정이나 배포를 변경하지 않는다. 운영 브랜치에 병합하면 자동
배포될 수 있으므로 승인 후 적용하고, 실제 문제가 났던 스캔으로 판독·QR·검수 결과를
확인한다. Render 메모리와 OOM 이벤트도 함께 관찰한다.

이 수치는 모든 입력/동시 업로드가 512MiB 안에 든다는 보증이 아니다. 압축 PDF 내부의
대형 이미지, 아주 큰 배치 결과의 base64 응답, 대기 중 multipart 업로드, 다중 서버
프로세스는 별도의 메모리를 쓸 수 있다. 기본 `OMR_MAX_CONCURRENCY=1` 및 단일
Uvicorn 프로세스를 유지하며 실제 요청 부하로 확인한다.
